## watchdog 性能优化（spark 报告驱动，用户给方案、我实施，未提交/未升版）

**问题**：`YanhuoSelectionScript.watchdogTick`（每刻任务）对「没选异火」的玩家负结果缓存不住
——`WD_SELECTED`（ConcurrentHashMap）不允许 null，旧代码用 `remove()` 表示"没有"，
下一刻 `sel == null` 又成立 → 每刻完整走 SQLite（prepareStatement 毫秒级）+ 两次 File.exists。
单人实测 8.2ms/刻、占主线程 16.4%，复杂度 O(在线人数)，6 人掉 TPS 到 12。

**落地（对照用户方案，6 项全做）**：
1. P0-1 哨兵：`NONE_SELECTED = "\u0000NONE"`，负结果也 `put` 进缓存；
   `EARTH_ID.equals(哨兵)` 恒 false，非厚土玩家照旧跳过。
2. P0-2 目录缓存：`YANHUO_DIR` volatile + 双检，首次 `configDir`（内含 ensure）后不再 stat。
3. P0-3 Store 读缓存：`DOC_CACHE`（组合键→原始 JSON 文本）+ `ABSENT` 负缓存；
   **缓存字符串不缓存 Map**——load 每次返回新解析副本，调用方就地改不污染缓存；
   save/delete/flush 同步维护；shutdown clear。
4. P1-1 语句复用：`Sqlite.STMTS`（HashMap，within 全局锁内天然串行）；
   select 复用 + clearParameters；SQLException 时踢出缓存并 close，下次重建；close() 清空。
5. P1-2 事件失效：`setSelected()` 末尾 `invalidateSelected()`（玩家自选与挑战清空都走它）；
   TTL 从 1s 放宽到 30s 作兜底。
6. P2：`PlayerKeys.key` 加 `length()==36` 快判；顺带 `AddonPaths.configRootPath()` 缓存
   （docParts 原来每读一份文档做两次 toPath().normalize()，watchdog 缓存命中后这就是剩余大头）。

**我在方案之外补的三处**（都是正确性洞）：
- **查询异常不缓存**：`Sqlite.select` 的 fallback 无法区分「正常无行」和「异常」——
  原方案会一次瞬时故障把「有档」固化成 ABSENT。现用 `ROW_MISSING`/`QUERY_ERROR` 两个内部哨兵区分；
  `exists()` 的 fallback 从 0 改 -1 同理。
- **exists 正向结果不写缓存**：DOC_CACHE 正向值必须是 load/save 放的完整文本，
  塞空串会让 load 把它当空白文档返回 null。
- **挑战期短路**：`isPhaseTwoLocked` 是纯内存查询——watchdog 锁定期间直接按未选中处理、
  不读也不污染缓存，只把时间戳顶新；解锁后下一刻立即过期重读存档。
  否则 30s TTL 会让「挑战结束异火恢复」延迟 30 秒（玩法回归）。

**幂等性核对**：watchdogTick 之后只用 `EARTH_ID.equals(sel)` ✓；非 watchdog 的 6 处
`selectedYanhuo()` 调用（事件/低频路径）不受影响且随 Store 读缓存一并提速；
`readJson` 的惰性迁移在 ABSENT 命中时照常回落读旧文件（迁移不被阻断）。

## watchdog 第二轮瘦身（用户给 v2.1.3 命名的优化构建跑了 spark，16.4% → 1.43%，watchdogTick 剩 1.03%）

新火焰图分析：剩余 1.03% 里 ~0.8% 是 Bukkit 遍历在线玩家的迭代器骨架（固有成本）、
0.21% 是每刻 CHM put、0.13% 是 isPhaseTwoLocked（hasMetadata）。SELECTED_TTL/Store 缓存已生效
（selectedYanhuo/readJson 均 0.00%）。

**本轮改动（核心洞察：每刻循环里只有厚土玩家才需要做实际工作）**：
1. `watchdogTick` 重排为「先判选中 → 非厚土立即 continue」：非厚土玩家不再做
   isDead + 2 次 CHM put + isPhaseTwoLocked(hasMetadata)，改为一条 `WD_LAST_HP.remove`
   （顺带建立不变量：WD_LAST_HP 只含厚土玩家，且防止长驻内存积累）。
2. `isPhaseTwoLocked` 只对 EARTH 缓存玩家查（挑战锁语义只是「视为未选中」，对非厚土无影响）
   → hasMetadata 从全员每刻降到厚土玩家每刻（通常 0 人）。
3. phase2 分支必须继续维护血量基准（第一版重排漏了，自查抓回：否则解锁后基准停在挑战前，
   挑战中掉的血会被错误回滚）。
4. `onDamageMonitor` 加 `WD_LAST_HP.containsKey` 过滤：非厚土受伤不再白做 merge+put
   （原来到 MONITOR 优先级才 return）。

其他热点评估结论：sugarTick 0.18%（27 tick 周期，读缓存已生效）、ScriptMachineItem.tick 0.09%、
Pofabow.tick 0.08% —— 均 <0.2%，改动风险大于收益，不动。

构建：exit 0，产物 TangranTech-2.1.4-standalone.jar 7,297,874 字节（11:19）。
